# Новые заказы в панели персонала

В панели добавлена строка состояния автообновления. При создании заказа список обновляется через Supabase Realtime. У администратора появляется уведомление, счётчик новых заказов и кнопка «Показать». Она переключает панель на заказы и снимает фильтр статуса. Уведомления работают также при открытой вкладке товаров или отчётов.

Кнопка динамика включает звук и сразу проигрывает пробный сигнал. Браузер требует этого нажатия для разрешения звука. После перезагрузки страницы звук нужно включить снова. В браузере используется короткий двойной сигнал; в настольном приложении — системный звук. На Android/iOS в этой версии доступны визуальные уведомления персоналу. Это оповещения при открытой панели, а не push после закрытия приложения.

## Настройка Supabase

В SQL Editor один раз выполните:

`supabase/migrations/202610130001_staff_order_realtime.sql`

Предыдущие миграции проекта должны уже быть применены. Новая миграция создаёт журнал `staff_order_events`, триггер изменений заказов, защищённую функцию чтения журнала и добавляет журнал в существующую публикацию `supabase_realtime`.

В Supabase Database → Publications проверьте, что `supabase_realtime` включает `public.staff_order_events`. Не добавляйте таблицу `orders` и не открывайте её для публичного чтения: она содержит секретные коды выдачи. Журнал содержит только версию события, ID заказа, тип изменения и время. Подробности заказа загружаются через RPC с проверкой роли сотрудника.

После применения миграции опубликуйте обновлённый клиент обычным push в `main` и дождитесь успешного GitHub Actions. Войдите администратором: статус должен смениться на «Заказы обновляются в реальном времени». Если WebSocket недоступен, включается резервная проверка каждые 10 секунд. При ошибках чтения отображается сообщение о повторном подключении. Фоновые вкладки могут обновляться реже из-за ограничений браузера; при возврате запускается немедленная проверка.

## Поведение и надёжность

- Старые заказы при открытии панели не вызывают звуковой сигнал.
- События доставляются через журнал с курсором; пропущенные события подгружаются после восстановления связи, в том числе более одной страницы.
- Один заказ не вызывает повторное уведомление в текущем сеансе. Смена статуса не считается новым заказом.
- Ручное обновление, фильтр и подгрузка страниц сохраняются; фоновое обновление не сбрасывает уже загруженный объём списка. Устаревшие ответы после смены фильтра или выхода игнорируются.
- При выходе из панели подписка и таймеры отключаются.
- Курсор упорядочен общей строкой ревизии, блокируемой до завершения транзакции. Это предотвращает пропуски из-за разного порядка коммитов и предназначено для масштаба одного кафе.
- В этой версии журнал хранится целиком. Нельзя вручную удалять его хвост или сбрасывать ревизию, пока работают клиенты с сохранённым в памяти курсором.

## Проверка

Откройте панель администратора в одном браузере и клиентское меню в другом/инкогнито. Включите звук. Оформите заказ с действующим слотом и остатком товара. Он должен появиться без ручного обновления, со счётчиком и сигналом. Повторите при открытой вкладке отчётов и при фильтре «Готов». Затем отключите сеть администратора, оформите ещё заказ и восстановите сеть: заказ должен догрузиться один раз.

Автоматические проверки:

```powershell
flutter analyze
flutter test
node test/sql/preorders.mjs
node test/web/staff_notification_sound_test.cjs
flutter build web --release --base-href /Cafe_Technikum/ --no-web-resources-cdn
```

SQL-тесты используют изолированный PGlite из предыдущей настройки проекта и не изменяют удалённую Supabase. Реальную доставку WebSocket и слышимость сигнала нужно проверить после применения миграции на работающем сайте.

API подписки: [Supabase Flutter Realtime](https://supabase.com/docs/reference/dart/subscribe).
