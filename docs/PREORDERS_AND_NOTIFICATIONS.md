# Предзаказы, остатки, выдача и уведомления

## Что реализовано

- В корзине обязателен выбор слота. Слоты, где не хватает места на **все порции корзины**, скрываются; остаются альтернативные времена.
- В панели администратора кнопка часов открывает расписание. На выбранную дату добавляются 10:00, 11:40 и 13:40 (перемены до 10:10, 12:10 и 13:50). Время кафе — UTC+4, независимо от часового пояса устройства.
- Готовность планируется к началу перемены. Приём закрывается за 5 минут. Начальный предлагаемый лимит — 30 порций; администратор задаёт его при создании и может менять нажатием на слот. Это рабочие значения для настройки, а не измеренная производительность кухни.
- Лимит учитывает сумму `qty`, включая повторяющиеся товары с разными добавками. Уже выданные заказы продолжают занимать мощность своего слота: работа кухни уже выполнена. Отмена освобождает мощность.
- В карточке товара администратор задаёт число свободных порций. `null` / пустое поле — без лимита, `0` — товар автоматически недоступен. Ручное выключение товара сохраняется отдельно от остатка.
- Слот и порции резервируются в одной транзакции PostgreSQL. Ошибка в любой позиции откатывает заказ и все резервы. Товары блокируются в стабильном порядке, изменение вместимости выполняется условным `UPDATE`.
- При отмене возвращаются только порции, которые действительно резервировались. Повторная отмена не увеличивает остатки. Отменённый/выданный заказ нельзя снова открыть. Неявившиеся заказы отменяет сотрудник.
- Жизненный цикл: создан → принят → готовится → готов → выдан. До выдачи возможна отмена. Выдача — отдельный RPC для кассира/администратора; бариста не выдаёт заказы.
- Новые QR содержат случайный код выдачи. Код возвращается только при создании и сохраняется на устройстве, не выдаётся публичным поиском заказа. Его можно снова открыть в отслеживании из «Мои заказы». Очистка данных приложения удаляет сохранённый код.
- Для старых заказов без слота поддерживается старый QR с ID. Для новых заказов ID/номер не заменяет секретный код.
- Сканирование камерой: Android/iOS/macOS/web. Windows/Linux: внешний USB-сканер с вводом в поле или вставка кода. Выдача требует готовности и оплаты; при оплате на кассе сотрудник ставит соответствующую отметку. Онлайн-оплата по-прежнему демонстрационная.
- В открытом гостевом приложении статусы сохранённых заказов проверяются каждые 15 секунд. При переходе в «Готов» показывается уведомление с переходом к заказу; статус сохраняется, повторное уведомление не показывается. Проверки приостанавливаются в фоне и возобновляются при возврате.
- Для Android добавлены подписка FCM, обработка нажатия на push, очередь отправки, повторные попытки и серверная функция. **Доставка после закрытия приложения требует настройки Firebase и развёртывания функции ниже.**

## Применение базы данных

На существующей базе должны быть применены обе старые миграции с префиксом `202604160003`: `clear_completed_staff_orders` и `customer_names`.

В Supabase SQL Editor выполните по порядку:

1. `supabase/migrations/202610020001_preorders_inventory_pickup.sql`
2. `supabase/migrations/202610020002_order_push.sql`

Каждая новая миграция обёрнута в транзакцию. Выполняйте её один раз. В старом наборе две миграции имеют одинаковый номер, поэтому для существующего проекта нельзя слепо использовать `supabase db push` без согласования истории миграций.

После миграции обновите клиент и создайте слоты в админ-панели. Старый клиент не передаёт слот и больше не сможет создавать заказы. Обновление клиента и БД нужно выполнять согласованно. Удалённая база автоматически этой доработкой не изменяется.

## Android push: настройка

1. Создайте/выберите проект Firebase и зарегистрируйте Android-приложение с текущим application ID `com.example.flutte2`. Если решите переименовать пакет, сначала согласованно измените Android-проект и регистрацию Firebase.
2. Скачайте `google-services.json` в `android/app/google-services.json`. Файл исключён из Git; Gradle подключает его только при наличии.
3. Соберите приложение с флагом:

   ```powershell
   flutter build apk --debug --dart-define=ENABLE_ANDROID_PUSH=true
   ```

   Supabase задаётся существующей конфигурацией проекта либо `SUPABASE_URL` и `SUPABASE_ANON_KEY` через `--dart-define`. Без флага Firebase не инициализируется. Для распространения нужна release-сборка и настройка подписи.

4. Включите Firebase Cloud Messaging HTTP v1 API. Создайте сервисный аккаунт с правами отправки FCM в этом проекте. Сохраните его JSON **только в секретах серверной Edge Function**, не в Flutter-приложении и не в Git.
5. В Supabase Edge Function Secrets задайте:
   - `FIREBASE_SERVICE_ACCOUNT` — полный JSON сервисного аккаунта Firebase.
   - `PUSH_WORKER_SECRET` — случайный секрет длиной не менее 32 байт.
   - `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` доступны развёрнутой функции в стандартном окружении Supabase.
6. Разверните функцию:

   ```powershell
   supabase functions deploy send-order-push --no-verify-jwt --project-ref YOUR_PROJECT_REF
   ```

   JWT отключён только у этой функции; она проверяет собственный заголовок `x-push-secret`. Публичный `anon`-ключ не даёт доступа к очереди и отправке.
7. В Supabase включите расширения `pg_cron` и `pg_net`. В Vault сохраните секреты `techcafe_project_url` (URL проекта) и `techcafe_push_worker_secret` (то же значение, что `PUSH_WORKER_SECRET`). Затем выполните `supabase/setup/order_push_schedule.sql`: функция будет запускаться каждую минуту.
8. На Android откройте оформленный заказ и нажмите «Уведомить о готовности на Android», разрешите уведомления. После первого согласия приложение пытается подключать активные локальные заказы автоматически при открытии их QR. Кнопка позволяет повторить подключение после ошибки. Подписки восстанавливаются при запуске и смене токена устройства.

FCM требует Google Play services. Android может ограничивать доставку настройками энергосбережжения и разрешений. После принудительной остановки приложения через настройки Android его нужно снова открыть. Обычное закрытие/сворачивание обрабатывается FCM. Проверка на реальном устройстве с настроенным Firebase обязательна.

Очередь формируется по событию изменения статуса в БД. До 30 сообщений обрабатываются за запуск, с арендой на 5 минут, максимум 8 попыток и экспоненциальными задержками. Отменённые/выданные заказы не выбираются для новых отправок. Повторные попытки могут создавать дубликаты: сбой после успешного FCM-запроса до подтверждения БД может вызвать повторную отправку; одинаковый Android notification tag заменяет карточку уведомления. Задания старше суток не отправляются. Очередь и подписки удаляются каскадно при удалении заказа; отдельную политику хранения для длительной эксплуатации следует задать администратору.

## Проверки

```powershell
flutter analyze
flutter test
npm install --prefix .dart_tool/sql-tests @electric-sql/pglite
node test/sql/preorders.mjs
flutter build web --release
flutter build apk --debug
```

SQL-тесты используют изолированный PostgreSQL WASM (PGlite), имитируя `auth.uid()` и роли Supabase. Применяется полный набор миграций. Проверяются переполнение слота, откат при недостатке товара, повторяющиеся позиции, возврат резерва, терминальные статусы, права ролей, оплата/одноразовая выдача, отсутствие секрета в публичном ответе, подписки и аренда очереди. Реальная конкурентная нагрузка на Supabase и доставка FCM требуют отдельной проверки в тестовом развёртывании.

Ручной сценарий: создать завтрашние слоты → задать 3 порции товара → заказать 2 → попробовать заказать ещё 2 → отменить первый заказ → заказать 3 → принять/готовить/готов → получить уведомление → отсканировать QR → подтвердить оплату и выдачу → повторно отсканировать (должен быть отказ).

Основания для интеграции: [Firebase — приём сообщений Flutter](https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages), [Firebase — отправка HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api), [Supabase — расписание Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions), [mobile_scanner](https://pub.dev/packages/mobile_scanner).
